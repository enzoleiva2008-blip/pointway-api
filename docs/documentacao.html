01 · Objetivo e escopo

Transformar engajamento digital em mobilidade real

A SoulUp identificou que grande parte dos pontos acumulados por seus usuários expira sem uso, enquanto o transporte público é uma necessidade diária — principalmente para a população de baixa renda. O Pointway resolve essa desconexão: o usuário converte pontos digitais em créditos de transporte, usados por meio de um voucher digital em ônibus, metrô, trem e BRT de operadoras parceiras.

O propósito do sistema é dar um destino concreto e cotidiano aos pontos SoulUp, gerando impacto ambiental mensurável (CO2 evitado) e inclusão social, ao reduzir o custo de transporte para quem mais depende dele.

O que mudou da Sprint 3 para a Sprint 4

Na Sprint 3 o projeto era uma aplicação Java com camada de modelo, DAO e uma classe de teste. Nesta entrega final ele virou uma API RESTful em Spring Boot, publicada na nuvem e consumida pelo front-end em React + Vite + TypeScript. As entidades, o banco e as regras de negócio foram mantidos; foram adicionadas a camada BO (validações e regras), a camada Resource (endpoints), o CorsFilter, o tratamento padronizado de erros e o deploy.

Escopo desta entrega: cadastro e gestão de usuários e operadoras; crédito de pontos; conversão de pontos em vouchers com regra antifraude; validação do voucher na catraca com registro da viagem e cálculo de CO2; painel do usuário e indicadores gerais de impacto; persistência em MySQL com CRUD completo das quatro tabelas.
Fora do escopo: integração real com os sistemas de bilhetagem das operadoras (SPTrans, Metrô, RioCard), autenticação de usuários e o aplicativo mobile. A validação na catraca é simulada pelo endpoint POST /viagens.
02 · Funcionalidades

O que a API entrega ao front-end

Cadastro de usuáriosCRUD completo, CPF validado pelos dígitos verificadores e único no sistema, e-mail validado.
Crédito de pontos SoulUpEndpoint para somar pontos ganhos na plataforma ao saldo do usuário, com limite por operação.
Operadoras parceirasCRUD com filtro por cidade; 4 operadoras já são cadastradas na primeira execução.
Conversão de pontos em voucher100 pontos = R$ 1,00, mínimo de 500 pontos, saldo verificado e debitado na emissão.
Prevenção de fraudeNo máximo 3 vouchers emitidos por usuário em 24 horas.
Voucher digitalCódigo único (UUID), validade de 30 dias, prorrogável até 90; vencidos viram EXPIRADO automaticamente.
Validação na catracaUso único: registra a viagem, marca o voucher como UTILIZADO e recusa voucher vencido ou já usado.
Cálculo de CO2 economizadoDistância × fator do modal (ônibus 0,09 · metrô 0,04 · trem 0,05 · BRT 0,07 kg/km).
Cancelamento com estornoVoucher ainda não usado pode ser cancelado e os pontos voltam ao saldo.
Painel e impactoResumo por usuário (saldo, vouchers, viagens, CO2) e indicadores gerais para a página inicial.
Erros padronizadosToda falha volta em JSON com status HTTP e mensagem pronta para exibir na tela.
Integridade dos dadosUsuário ou operadora com vouchers vinculados não pode ser excluído.

05 · Modelo de Entidade-Relacionamento

Estrutura do banco de dados

O banco é o mesmo da Sprint 3 (MySQL). As tabelas são criadas automaticamente pela API ao iniciar, a partir de schema.sql.

RelacionamentoCardinalidadeRegra
USUARIOS → VOUCHERS1 : NUm usuário converte pontos em vários vouchers (fk_voucher_usuario).
OPERADORAS → VOUCHERS1 : NCada voucher vale em uma operadora (fk_voucher_operadora).
VOUCHERS → VIAGENS1 : N (na prática 1 : 1)O voucher é de uso único; a regra de negócio garante uma viagem por voucher (fk_viagem_voucher).
06 · Diagrama de classes

Camadas da aplicação

Fluxo de uma requisição: Resource (recebe o HTTP) → BO (valida e aplica regras) → DAO (SQL via ConnectionFactory) → MySQL. O model carrega as regras de domínio.

07 · Procedimentos para rodar a aplicação

Do zero até a API no ar

Ferramentas e versões

ItemVersão
Java JDK17 ou superior
Spring Boot3.5.6
Maven3.9+
MySQL8.x
IDEIntelliJ IDEA, Eclipse ou VS Code (Extension Pack for Java)
TestesPostman, Insomnia ou requests.http

Importar o projeto

IntelliJ: File > Open > pasta pointway-api (com o pom.xml).

Eclipse: File > Import > Maven > Existing Maven Projects.

VS Code: abrir a pasta com o Extension Pack for Java.

O Maven baixa o Spring Boot e o driver do MySQL sozinho.

Executar localmente

  1. Iniciar o MySQL e criar o banco: CREATE DATABASE pointway_db; (ou rodar database/pointway_schema.sql).
  2. Conferir usuário e senha do banco em dao/ConnectionFactory.java (padrão root/root). Também é possível usar as variáveis de ambiente DB_URL, DB_USER e DB_PASSWORD.
  3. Executar a classe PointwayApplication pela IDE, ou no terminal: mvn spring-boot:run.
  4. Abrir http://localhost:8080/ — deve aparecer "status": "online". As tabelas e 4 operadoras de exemplo são criadas na primeira execução.
  5. Testar os endpoints com o arquivo requests.http ou pelo Postman.
07 · Procedimentos (continuação)

Deploy na nuvem (Railway)

  1. Publicar o projeto no GitHub.
  2. No Railway: New Project > Deploy from GitHub repo. O Dockerfile do projeto é detectado e a API é compilada com Maven e executada com Java 17.
  3. No mesmo projeto: + New > Database > MySQL.
  4. No serviço da API, aba Variables, criar DB_URL, DB_USER e DB_PASSWORD apontando para o MySQL do Railway (valores no README).
  5. Settings > Networking > Generate Domain: o link gerado é a URL da API usada pelo front-end na Vercel.
DB_URL=jdbc:mysql://${{MySQL.MYSQLHOST}}:${{MySQL.MYSQLPORT}}/${{MySQL.MYSQLDATABASE}}?useSSL=false&allowPublicKeyRetrieval=true
DB_USER=${{MySQL.MYSQLUSER}}
DB_PASSWORD=${{MySQL.MYSQLPASSWORD}}

Integração com o front-end

O CorsFilter libera chamadas vindas de outro domínio (a Vercel) e responde às requisições preflight (OPTIONS). No React, a URL da API fica na variável VITE_API_URL:

const resp = await fetch(`${import.meta.env.VITE_API_URL}/vouchers`, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ usuarioId: 1, operadoraId: 1, pontos: 800 }),
});
if (!resp.ok) alert((await resp.json()).mensagem);

Boas práticas aplicadas

  • Padrões DAO, Connection Factory e MVC (Resource → BO → DAO → Model).
  • Injeção de dependência pelo construtor e nomes em português seguindo a convenção Java.
  • PreparedStatement em todo SQL (evita SQL Injection) e try-with-resources para fechar conexões.
  • Exceções próprias (ValidacaoException, RegraNegocioException, ConflitoException, RecursoNaoEncontradoException) convertidas em status HTTP pelo GlobalExceptionHandler.
  • Status REST corretos: 201 com header Location na criação, 204 na remoção.
